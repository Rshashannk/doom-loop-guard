# PRD: doom-loop-guard v0.2, loop and spend control for teams

**Date:** 2026-11-26 · **Status:** reviewed (built; awaiting Shashannk's go-ahead to merge) · **Owner:** Shashannk

## Problem
v0.1 stops one kind of loop: the agent hitting the same error, or re-running the same failing command. Research done on 2026-11-26 shows the costly loops are often a different kind:

- **Loops with no error.** In the arXiv study of 6,549 agent repos (2607.01641), every one of the 68 confirmed infinite loops came from a *missing strong bound*. 95.6% of them led to API cost exhaustion. Many retried or iterated without any tool ever failing, so an error-based guard never sees them.
- **Whole-file rewrites.** A user on X (2026-11-25): "one of mine used up the whole day's limit in 8 hours, rewriting entire files when it only needed to change a few lines." No error at all, just repeated `Write` of the same file.
- **Retry loops inside subagents.** Claude Code issue #46968: one subagent burned about 101k tokens retrying on "File has been modified since read". That validation error may never reach a hook, so only a budget would catch it.
- **No real-time halt in companies.** VentureBeat Pulse (n=107, self-selected, July 2026): 21% of enterprises track agent spend only in logs after the fact, with no way to halt a runaway run. Claude Code's own spend limits are per org, group or member per month. `--max-budget-usd` exists for headless runs only. Neither one stops a single interactive session at a sane size.

## Target user
1. A developer who wants a session capped before it eats the day's limit.
2. A platform or IT admin who needs every developer's Claude Code to have the same loop and spend bounds. They also need a local record of every trip, and a policy that a developer or a repo can't quietly turn off.

## Success metrics
| Metric | Baseline | Target |

## MVP stories (P0)
1. **Rewrite churn.** As a developer, I want to be warned when the agent rewrites the same existing file with `Write` again and again, so I stop paying for whole files when a few lines changed.
   - The 3rd full rewrite of an existing file in a session adds a warning that names the file, the count and the line count, and says to use Edit. Creating a new file does not count.
   - `rewriteChurn.stop` (off by default) stops the session at that count. This applies to every file type, including docs.
2. **Identical calls.** As a developer, I want a loop of the exact same tool call with the same input to be caught even when nothing fails.
   - The 5th identical call in a row warns. The 10th stops (deny + `continue:false`).
   - Any different call in between resets the count. Ignored commands (grep, sleep, and similar) never count.
3. **Session budgets.** As an admin, I want a hard bound per session on tokens and on tool calls.
   - Tokens are read from the session transcript: each assistant message is counted once, as input + cache writes + output. Cache reads are tracked but not counted.
   - The transcript is read incrementally, so each hook reads only the new bytes. A partly written last line waits for the next hook.
   - `budget.tokens` and `budget.toolCalls` each have `warn` and `stop`, all off by default.
   - A stop fires on the next tool call. If the user tells the agent to continue, the next stop comes at 2× the limit, then 3×, and so on.
4. **Managed policy.** As an admin, I want a policy file that wins over user and project config.
   - It lives next to Claude Code's managed-settings.json:
     - Linux: `/etc/claude-code/doom-loop-guard.json`
     - macOS: `/Library/Application Support/ClaudeCode/doom-loop-guard.json`
     - Windows: `C:\Program Files\ClaudeCode\doom-loop-guard.json`
   - With `"lock": true`, these switches are ignored: `DOOM_LOOP_GUARD=off|warn`, `.doom-loop-guard-off`, and any `mode` set in user or project config.
   - `DOOM_LOOP_GUARD_POLICY` is only used when no system file exists, for CI and tests.
5. **Audit log.** As an admin, I want every warning and stop written locally as one JSON line.
   - Each line records time, rule, kind, session, agent, project, tokens, tool calls, plugin version and reason.
   - The default file is `~/.claude/doom-loop-guard/audit.jsonl`. Policy or user config can move it (not project config). It rotates at 10 MB.
   - `node scripts/stats.js` summarizes it, so it can be shipped with an existing log agent. Nothing is sent anywhere.
6. **Enterprise guide.** `docs/ENTERPRISE.md` explains how to roll this out with managed settings:
   - (a) as a plugin force-enabled with `enabledPlugins` from a known marketplace. This works even with `allowManagedHooksOnly`, because force-enabled plugins are exempt.
   - (b) as a managed hook from a fixed install path, for machines that can't reach GitHub.
   - It includes example policy and managed-settings files.

## Out of scope
- Any network call, telemetry or account. Enterprises must be able to audit that it phones nowhere.
- Replacing Claude Code's org spend limits. This bounds one session; their limits bound the month.

## Decided
- New stop rules default to off, except identical calls at 10. There is no evidence for a universal token threshold, so admins set budgets in policy.
- Tokens come from the transcript because hooks receive no usage data. The transcript format is not a public contract, so a parse failure must disable only the budget, never the hook.

## Open questions & assumptions
- Verified in a live run on Claude Code 2.1.332: `Write` returns `tool_response.type: "update"` for an existing file. If the field is ever missing, the PreToolUse existence check decides.
- Verified in the Claude Code docs: `allowManagedHooksOnly` blocks plugin hooks, except plugins force-enabled in managed `enabledPlugins`.
- Found in QA: the transcript is flushed a little after each model turn, so the token count can lag by about one turn. That is fine for a session bound, but it is not exact to the token.
